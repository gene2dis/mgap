# Coverage, read QC and Kraken2/Bracken benchmark (2026-10-24)

Benchmark for the 2026 review items E2 (coverage estimate and ONT read reduction), F2 (fastplong thresholds), E4
(Kraken2 memory mapping) and B10 (Bracken read length); the review and roadmap are kept outside the repository, and
"Phase 6a/6b" below refer to its benchmark and apply steps. Nothing in the pipeline changed for this benchmark: every variant ran the
`dev` code (a556fd7) with a `-c` config or a standalone tool call, listed in [Reproducing](#reproducing). Phase 6b applies
what is approved.

Setup: Nextflow 26.04.4, `-profile docker`, each variant in its own launch, work and output directory, at most 24 CPUs per
run (`executor.cpus`). The server (80 cores) was shared and loaded throughout (load average 90–220), so wall times carry
about ±30 % noise: the same three SPAdes jobs, rerun on identical input, took 22.7/17.8/31.4 min once and 31.6/22.3/41.8
min the other time. Compare runs side by side, not with other machines. Task times and peak memory come from Nextflow's
`execution_trace` (`realtime`, `peak_rss`).

Data (in-house isolates, not distributed): the Illumina routing set at ~100x (10 samples), three of the same samples at full depth
(SCL2333 K. pneumoniae, SCL1559 S. aureus, 100.1 S. enterica), the ONT fixture SCL10571 at ~100x (K. pneumoniae ST11,
plasmids of 239, 190, 110, 54 kb and 5.2, 4.5, 4.2, 3.9 kb, known from an earlier Autocycler and Plassembler run), SCL25346 at full depth (~250x, ST25) and
SCL4611 (old R10.4 chemistry, Q14) for read QC. CheckM2 database `uniref100.KO.1.dmnd`.

Found on the way (not part of these items):

- **Boolean parameters cannot be switched off on the command line.** With Nextflow 26.04, `--adjust_coverage false`
  arrives as the string `"false"`, which Groovy treats as true; `--run_kraken2 false` and `--run_dnaapler false` are
  affected the same way. Setting them in a `-c` config or a `-params-file` works. Checked with a two-line script
  (`params.x = true`; `--x false` → `false class java.lang.String truthy`) and in this benchmark (Mash ran with
  `--adjust_coverage false`).
- `MASH_SKETCH`'s comment says Mash reports one coverage line per input file; with `-r` it sketches R1 and R2 together and
  prints one line, so the sum is that one value.
- `MASH_SKETCH` re-emits the reads from its own work directory, so the SPAdes task hash differs between
  `adjust_coverage` on and off even when no reads are dropped (no `-resume` reuse).
- Flye's `*.assembly.fasta.gz` and `*.assembly_graph.gfa.gz` are not published (the `FLYE` publish pattern has no `gz`).
- The nf-core `seqtk/sample` module appends `-s100` unless `ext.args` matches `/.*\ -s\ ?[0-9]+.*/`, which needs a space
  before `-s`: `ext.args = '-s 11'` runs `seqtk sample -s 11 -s100` and seed 100 wins. Write `' -s 11'`. The pipeline sets
  no seed today, so it is not affected.

sequencing errors included, counts as genome. The pipeline then subsamples with Seqtk when Mash's coverage exceeds
`max_coverage` (110).

and assembled with SPAdes `--isolate` as in the pipeline. The fraction is target × assembled length ÷ fastp output bases,
so the depths are real base coverage, not Mash's figure. Seed 100 is Seqtk's default, the one the pipeline uses; seeds 11
and 22 are the replicates. 42 assemblies, one launch per seed set, at most 36 CPUs, same shared-server noise as above.

- **N50 moves as much with the seed as with the depth.** SCL1559's N50 spans 135–203 kb at each depth from 50x to
  110x and 159–203 kb at 150–200x, depending on the seed; single differences in N50 of this size are noise.
- **100.1 and SCL1559 level off by 110x** in contigs, length and N50. Below that, some 100.1 seeds lose a join (50–80x:
  N50 183 kb). Sequence missing from the full assembly is at most 3.7 kb at any depth, and falls to 0–1.1 kb from 150x.
- **SCL2333, the largest and most fragmented genome, still gains at 110x.** 50x is clearly worse (134–140 contigs, N50
  84–89 kb, 28–34 kb shorter); 80x is in between; 110x (86–95 contigs, N50 159–211 kb) is close to the full 138x
  assembly but every seed is 8–10 kb shorter. The sample has no depth above 138x to test.
- **From 110x to 244x nothing improves or degrades** (contigs, length, N50, CheckM2). No sample here is above 300x, the
  range where SPAdes is reported to degrade, so whether subsampling helps quality at very high depth is untested.
- SPAdes time grows roughly linearly with depth (100.1: 5–6 min at 50x, 21 min at 244x).

So 110x real coverage sits at the start of the plateau for the hardest of the three genomes, and 150x (Shovill's default
target) is inside it for all three. With the estimate fixed, `max_coverage` 150 subsamples only samples that gain nothing
from the extra reads.

`--asm-coverage` picks the longest reads for the disjointigs, and a 4 kb plasmid is carried by short reads, so the small
plasmids never get a disjointig. Random subsampling keeps reads in proportion, and these plasmids are high-copy
(400–1,500x), so it keeps them. This is the opposite of the assumption behind the plan ("small plasmids are carried by short reads that subsampling
can drop"). Only `--asm-coverage 40` was tested (Flye's help: "Typically, 40x coverage is enough to produce good
disjointigs"); a higher value would keep more short reads but save less time.

  low-quality data (SCL4611 keeps 87 % instead of 80 % with `--mean_qual 10`); its assembly was not compared.

## E4 · Kraken2 `--memory-mapping`

The pipeline's image (`kraken2_coreutils_pigz:920ecc6b96e2ba71`, Kraken2 2.1.6), standard database (Dec 2022, 62.3 GB
`hash.k2d`), the fastp reads of the ~100x routing set, 12 threads, `docker run --memory <limit>` as Nextflow does. The
container's memory charge (`memory.current`, cgroup v2) and the summed process RSS were sampled every second. A cold
cache was made by dropping the file from the page cache (`posix_fadvise(DONTNEED)`, checked with `fincore`).

SCL1880, one task at a time:

| Cache, mapping, limit   |                Wall |          Classifying |  Load | Container charge (anon + file)              | Process RSS |
| ----------------------- | ------------------: | -------------------: | ----: | ------------------------------------------- | ----------: |
| cold, off, 72 GB        |               438 s |                 52 s | 386 s | 72.0 GB (62.9 + page cache up to the limit) |     62.9 GB |
| 9 GB cached, off, 72 GB |               444 s |                 67 s | 378 s | 72.0 GB                                     |     62.9 GB |
| cold, on, 72 GB         |               178 s | 164 s (loads lazily) |     — | 63.2 GB (0.6 + 62.3 file)                   |     57.5 GB |
| 18 GB cached, on, 72 GB |               182 s |                171 s |     — | 45.3 GB                                     |     57.6 GB |
| warm, on, 8 GB          |               113 s |                 89 s |     — | 0.8 GB                                      |     57.6 GB |
| cold, on, 16 GB         | killed after 43 min |                    — |     — | 16.0 GB, 4.4 TB read from disk              |           — |

All ten samples, warm cache, one at a time (with three at a time in brackets for 100.1, SCL2273, SCL2535):

|                                   | Mapping off                                  | Mapping on                    |
| --------------------------------- | -------------------------------------------- | ----------------------------- |
| Wall per sample                   | 147–216 s, sum 1,829 s (145–193 s)           | 46–148 s, sum 816 s (56–83 s) |
| Load time (wall − classifying)    | 125 s on average                             | 9 s on average                |
| Container charge per task         | 63.0–63.5 GB                                 | 0.7–1.2 GB                    |
| Process RSS (Nextflow `peak_rss`) | 62.9–63.4 GB                                 | 52.7–62.2 GB                  |
| Reports                           | byte-identical to mapping on, all 10 samples |                               |

- Without mapping each task copies the database into its own memory. In a 72 GB container that leaves 9 GB for page
  cache, so the file is never fully cached by the pipeline itself: every `KRAKEN2` task pays the 6–7 min cold load here
  unless something outside the containers keeps the file cached.
- With mapping, pages already in the page cache are shared and not charged again, so concurrent tasks cost ~1 GB each.
  But the task that first reads a page is charged for it: on a cold cache the first task is charged 63 GB, and under a
  16 GB limit it evicted its own pages and re-read them until killed. The memory request therefore stays at the
  database size plus a little: 72 GB (`process_high`) is right for this 62 GB database; dropping it is only safe when
  the database is known to be cached.
- Nextflow's `peak_rss` counts mapped file pages, so a mapped task still shows ~60 GB in the trace and report although
  the container is charged ~1 GB when the cache is warm.
- Cloud profiles: each task starts on a fresh machine with an empty cache and the database on a network disk. Mapping
  then turns one sequential read into random page faults over 62 GB; that was not measured (no cloud account), and there
  is no cache to share. Keep it off there.

Proposed rule for 6b: read `total_cycles` from each sample's fastp JSON, list the `database<N>mers.kmer_distrib` files in
the Bracken database once at launch, and pass the largest N at or below the cycle count as `-r` through `ext.args`
(from `meta`); a `--bracken_read_length` param overrides it. If no length fits (reads shorter than the smallest
distribution), warn and use the smallest.

## Reproducing

Scratchpad configs used with `-c` (the pipeline itself unchanged):

```groovy
// cap per run
executor { cpus = 24 }
// Mash k32 m3
process { withName: MASH_SKETCH { ext.args = '-k 32 -m 3' } }
// no reduction (a -c config: `--adjust_coverage false` on the command line is ignored, see above)
params.adjust_coverage = false
// Flye asm-coverage, genome size from the earlier Autocycler (Raven) estimate
process {
    withName: FLYE {
        ext.args = { "--asm-coverage 40 --genome-size ${[SCL10571: '5.93m', SCL25346: '5.63m'][meta.id]}" }
    }
}
// forced Seqtk on the ONT fixture (today's Mash says 15x for 81x)
params.max_coverage = 10
```

Depth sweep: a standalone workflow including the pipeline's `FASTP` (same `ext.args`), `SEQTK_SAMPLE`, `SPADES`
(`--isolate`), `QUAST`, `SEQKIT_FILTER` (`--min-len 1000`) and `CHECKM2_PREDICT` modules, with
`SEQTK_SAMPLE` `ext.args = { " -s ${meta.seed}" }` and `executor { cpus = 36 }`.
